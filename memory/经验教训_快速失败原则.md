# 经验教训：数据采集流程中的"快速失败"原则

> 来源：2026-05-22 Yahoo 1h 数据回溯采集事故
> 教训：Yahoo 1h API 限制730天，请求3年数据时返回空，采集程序陷入重试循环 → Chrome OOM → SIGKILL

---

## 快速失败的两层含义

### 一、技术层失败（Technical Fail Fast）

**触发条件：网络、认证、程序错误导致的请求无法完成**

| 场景 | 表现 | 处理 |
|------|------|------|
| 网络超时 | 请求超时 | 重试 1-2 次，仍失败则退出 |
| HTTP 错误码 | 4xx/5xx | 4xx 不重试（客户端问题），5xx 可重试1次 |
| 连接被拒绝 | Chrome CDP 无响应 | 立即退出，不要持续重试 |
| 页面加载失败 | resp.status != 200 | 不重试，直接标记失败 |
| JSON 解析失败 | 正则/JSON 解析异常 | 不重试，直接标记失败 |

**原则：技术层失败最多重试 1-2 次，且要有退避策略（exponential backoff）。超过则立即退出，不要陷入无限重试。**

---

### 二、业务层失败（Business Fail Fast）

**触发条件：HTTP 请求成功（200），但返回数据不符合预期**

这是更重要的失败层，也是最容易忽视的：

| 场景 | 表现 | 处理 |
|------|------|------|
| 空数据 | `len(data) == 0` | **立即失败，不重试** |
| 数据不足 | 实际条数 < 预期最小量 | **立即失败，不重试** |
| 错误信息 | Yahoo 返回 error 字段 | **立即失败，不重试** |
| 数据过期 | 最新数据日期 << 今天 | 立即失败，提示数据源问题 |
| 字段缺失 | OHLCV 关键字段缺失 | 立即失败，不重试 |

**核心原则：HTTP 200 ≠ 数据获取成功。请求成功只是"连接通了"，必须验证返回的数据是否符合业务预期。**

---

## 业务层验证清单（每次请求后必做）

```
1. result is not None and len(result) > 0
2. timestamp 列表不为空
3. quote 列表不为空
4. 实际返回条数 >= 预期最小条数（比如请求30天，至少应有20+条）
5. 不存在 error 字段
```

## 实践代码模式

```python
def fetch_one(page, symbol, p1, p2, interval):
    r = page.goto(chart_url, timeout=PAGE_TIMEOUT_MS)
    if not r or r.status != 200:
        raise TechnicalError(f"HTTP {r.status}")  # 技术层失败

    content = page.content()
    chart_data = parse_json(content)  # 技术层失败（JSON解析）

    result = chart_data.get("chart", {}).get("result", [])
    if not result:
        raise BusinessError("API返回空result")  # 业务层失败

    r0 = result[0]
    timestamps = r0.get("timestamp", [])
    if not timestamps:
        raise BusinessError("无timestamp数据")  # 业务层失败

    # 业务层：验证数据量是否合理
    expected_min = estimate_expected_bars(p1, p2, interval)
    if len(timestamps) < expected_min * 0.5:  # 实际少于预期的50%
        raise BusinessError(f"数据量异常: 期望~{expected_min}, 实际{len(timestamps)}")

    return data
```

## 重试策略

| 错误类型 | 可重试？ | 次数 | 说明 |
|----------|---------|------|------|
| 网络超时 | ✅ | 1-2次 | 加退避 |
| HTTP 5xx | ✅ | 1次 | 服务器问题，可能恢复 |
| HTTP 4xx | ❌ | 0次 | 客户端问题，重试无用 |
| JSON解析失败 | ❌ | 0次 | 格式问题，不会自己修复 |
| 空数据/数据不足 | ❌ | 0次 | **Yahoo硬限制，重试无意义** |

---

## 教训关联

- **Yahoo 1h 数据硬限制：约 730 天**。超过此范围的数据不存在，重试100次结果一样
- 大数据量请求（3年1h）→ Yahoo 返回空 → 重试循环 → Chrome OOM → 系统杀进程
- **预防方法**：请求前判断区间是否超过 API 限制，超过则切分为多个小请求

## 新需求验证：小 Demo 优先原则

**触发场景**：引入新的 API、新的数据源、新的策略逻辑、或对现有流程做重大修改时

**核心原则**：先小范围测试，确认可用后再大规模调用

### 为什么必须这样做

1. **避免资源浪费**：大规模调用失败 → 浪费大量时间和计算资源
2. **快速暴露问题**：1-3只股票能暴露的问题，569只同样会暴露，且更早发现
3. **降低回滚成本**：小范围验证失败 = 修改1个脚本；大规模失败 = 可能需要清理半成品数据
4. **验证 API 稳定性**：新 API 可能有隐藏限制（条数、频率、字段），小流量即可发现

### 标准验证流程

```
第一步：选定 1-3 只代表性股票
       - SPY（大盘指）
       - AAPL（高流动性大盘股）
       - 1只低流动性股票

第二步：单次请求测试
       - 检查 HTTP 状态码
       - 检查返回数据量和内容
       - 检查数据日期范围是否符合预期

第三步：连续 3-5 次请求测试（模拟增量更新）
       - 验证去重逻辑
       - 验证增量追加逻辑
       - 验证数据不丢失

第四步：确认 OK 后再全量跑
```

### 快速验证脚本模板

```python
def quick_verify(symbols, interval, days=730):
    """30行以内，验证新接口是否可用"""
    results = {}
    for sym in symbols:
        try:
            data = fetch_one(sym, interval, days)
            # 业务层验证
            assert len(data) > 0, f"{sym}: 空数据"
            assert 'close' in data[0], f"{sym}: 字段缺失"
            results[sym] = "OK"
        except Exception as e:
            results[sym] = f"FAIL: {e}"
    return results

# 先跑这个，确认OK再大规模
print(quick_verify(['SPY', 'AAPL', 'MSFT'], '1h'))
```

### 血的教训

- **今天（2026-05-22）**：未做小 Demo 验证，直接全量 569 只股票回溯 3 年 1h 数据
  → Yahoo 730天硬限制 → 空数据 → 重试循环 → Chrome OOM → SIGKILL

- **正确做法**：先拿 SPY 一只股票验证 1h range=2y，确认能拿到 ~500 条数据，再全量

## 后台运行 + 最高权限停止原则

**触发场景**：所有数据获取类需求（fetch / 抓取 / 下载 / 更新数据）

### 为什么必须在后台

1. **用户可随时干预**：发现问题 → 喊停 → 立即响应
2. **不阻塞主对话**：主session可以继续响应其他问题
3. **方便监控状态**：通过 process 工具查看进度 / 日志 / 残留
4. **便于紧急kill**：发现问题可立即SIGKILL，不用等超时

### 操作规范

```
启动：background=true，后台运行
监控：process poll/log 查看进度
停止：process kill（最高权限），立即SIGKILL
```

### 停止时的最高权限策略

```bash
# 第一步：温柔通知进程退出
kill <pid>

# 第二步：等待5秒，若未退出则SIGKILL
kill -9 <pid>   # SIGKILL，不可捕获，强制立即终止

# 第三步：检查残留进程
ps aux | grep fetch
```

### 快速停止检查清单

当用户喊"停止"时，立即执行：
```
1. kill 所有相关进程（fetch_us_stocks / playwright / chromium）
2. 确认 Chrome CDP 端口无残留连接
3. 确认进程已完全退出
4. 报告已停止
```

### 今天的事故（2026-05-22）

- 用户喊了两次"停止数据获取"，但进程是 SIGKILL 被系统杀的，不是及时响应
- 原因：进程陷入死循环（重试），无法优雅退出
- **改进**：加入业务层快速失败后，进程不会陷入死循环，stop 命令可以立即生效
